# Todo Exercise

A simple Rails 8.1 todo app used as context for technical interviews. You're
welcome to run it locally — doing so may help you build familiarity, but it's
not required.

## About the application

This app was built primarily using Rails generators and scaffolding, which is
representative of how most Rails teams start new resources. It manages two
models: `User` and `Todo`, with a straightforward has-many/belongs-to
relationship. There is no authentication.

The frontend uses [Tailwind CSS](https://tailwindcss.com/) (via
[`tailwindcss-rails`](https://github.com/rails/tailwindcss-rails)), which
provides simple but functional styling without a custom design system. Views
were generated by the scaffold and lightly adjusted — intentionally close to
what Rails produces out of the box.

The stack:

- **[Rails 8.1](https://guides.rubyonrails.org/)** with
  [Propshaft](https://github.com/rails/propshaft) for assets and
  [Importmap](https://github.com/rails/importmap-rails) for JavaScript
- **[PostgreSQL](https://www.postgresql.org/)** as the database
- **[Hotwire](https://hotwired.dev/)** ([Turbo](https://turbo.hotwired.dev/) +
  [Stimulus](https://stimulus.hotwired.dev/)) included by default, lightly used
- **[Minitest](https://github.com/minitest/minitest)** for unit, controller, and
  system tests
- **[RuboCop](https://rubocop.org/)**
  ([rubocop-rails-omakase](https://github.com/rails/rubocop-rails-omakase)) for
  linting
- **[Brakeman](https://brakemanscanner.org/)** and
  [bundler-audit](https://github.com/rubysec/bundler-audit) for security
  scanning

## Environments

For the purposes of this exercise, assume the application is deployed in two
environments beyond local development:

- **Non-production** — used by the engineering team for testing and review.
  Changes here carry less risk but disruption still matters as other engineers
  rely on it.
- **Production** — live and expected to remain stable and available. Changes
  must be made carefully and with appropriate consideration for rollback and
  impact. Production holds real user data including personally identifiable
  information (PII), which must be handled and protected accordingly.

## Getting started locally

Docker is the recommended way to run the app.

**Requirements:** [Docker](https://docs.docker.com/get-started/) and Docker Compose.

```sh
make setup      # Build containers and setup database
make seed       # load sample data (2 users, 5 todos)
make start      # start the app (docker compose up -d)
```

Open http://localhost:3000/users or http://localhost:3000/todos — there is no
root route.

```sh
make logs       # follow container logs
make stop       # shut everything down
```

## Running tests

```sh
# Build containers and setup database
make setup

# Full test suite (matches CI)
make test

# Single file
docker compose run --rm -e RAILS_ENV=test web rails test test/models/todo_test.rb

# Single test by line number
docker compose run --rm -e RAILS_ENV=test web rails test test/controllers/todos_controller_test.rb:42

# System tests
docker compose run --rm -e RAILS_ENV=test web rails test:system
```

## Linting and security

```sh
docker compose run --rm web bin/rubocop
docker compose run --rm web bin/brakeman --no-pager
docker compose run --rm web bin/bundler-audit
```

## Cleanup

```sh
make purge # stop containers and remove images all artefacts
```

## CI

[GitHub Actions](https://docs.github.com/en/actions) runs on every PR and push
to `main`: Ruby and JS security scans, RuboCop linting, and the full Minitest
suite (including system tests) against a real Postgres service container.
